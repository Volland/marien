# Spike result: one Lean runtime inside LadybugDB

Date 2026-10-31. LadybugDB v0.22.1 (release CLI and `liblbug` as hosts, source headers at the
tag), Lean 4.35.0, LeanElpi v0.3.3. Change: `openspec/changes/archive/2026-10-31-spike-lean-runtime-in-ladybug`.

| Platform | Verdict |
|---|---|
| macOS arm64 | **Go.** Every check passes; 2.7 MB, 0.8 MB gzipped, about 12 ms to load. |
| Linux aarch64 (Docker; x86_64 uses the same toolchain build, not yet run) | **Go with a rebuilt `libleanrt.a`** (`scripts/build-leanrt-pic.sh`: PIC, global-dynamic TLS, libstdc++). Every check passes; 3.8 MB, 1.2 MB gzipped, about 8 ms to load. The stock toolchain archive crashes on load (local-exec TLS). |

## Loader contract (task 1.1)

`ExtensionLibLoader` (`src/extension/extension.cpp`) calls `dlopen(path, RTLD_NOW | RTLD_LOCAL)`
and `dlsym`s two C symbols. `name` (`const char*()`) lets `ExtensionManager::loadExtension` skip
an extension already loaded in that database. `init` (`void(lbug::main::ClientContext*)`)
registers functions. `load` and `install` are looked up only for official extensions. On macOS,
official extensions link with `-undefined dynamic_lookup` and resolve LadybugDB symbols from the
host; the release CLI and `liblbug` both export them. All 18 LadybugDB symbols the shim needs were
present. `common/system_config.h` is generated by CMake and is part of the ABI, so the shim is
compiled against a configured tree of the same tag. Release binaries use the OS C++ runtime:
`/usr/lib/libc++.1.dylib` on macOS and libstdc++ on Linux.

| Check | Result |

| Stress (`stress stress`) | 16 threads × 1000 calls: 0 failures, 0.67 s; 16 × 4000: 0 failures; RSS +8–9 MB in both runs (no growth per call) |

The official `algo` 0.22 package cannot be loaded on macOS: `libalgo.lbug_extension` needs
`@rpath/libnetworkit.dylib` and its rpaths point at the CI runner (`/Users/runner/work/...`).
That is an upstream packaging bug, so the coexistence check uses `fts` and `vector`, two official
extensions that also bundle native code.

### Size (task 2.5)

| Link | Uncompressed | gzip -9 | xz -9 |
|---|---|---|---|
| `-dead_strip`, runtime-only `lean_initialize` | 2.68 MB | 0.83 MB | 0.56 MB |
| no dead-strip, runtime-only `lean_initialize` | 10.95 MB | 3.21 MB | 1.92 MB |
| `-dead_strip`, toolchain `lean_initialize` (`libleancpp`) | 67.9 MB | 24.1 MB | 12.6 MB |
| no dead-strip, toolchain `lean_initialize` | 111.0 MB | 36.0 MB | 18.4 MB |

The design expected about 45 MB. The difference comes from one finding: Lean 4.35 emits a call to
`lean_initialize()` at the start of every module initializer (`.lake/build/ir/Spike.c`), and the
toolchain's definition in `libleancpp` runs `initialize_Lean`, the whole compiler package (found
with `ld -why_live _initialize_Lean`). LeanElpi's core imports only `Lean.Data.PersistentHashMap`
and `Lean.Data.PersistentArray`. `bridge.c` therefore defines a guarded `lean_initialize` that
starts only the runtime, and `libleancpp` is not linked, so the linker pulls in only the modules
actually imported. This is ADR 0022. LeanElpi's own `libleanelpi` would shrink the same way.

## Linux evidence (task 1.5)

Run with `spike/linux/docker.sh` (Ubuntu 24.04, g++ 13, LadybugDB v0.22.1 `liblbug` and CLI for
linux-aarch64).

1. **Link order.** GNU ld scans archives once, so the Lean archives are linked inside
   `--start-group … --end-group`.
2. **Two C++ standard libraries.** The Linux Lean toolchain builds its runtime against its own
   static libc++ (`std::__1`); LadybugDB and the shim use libstdc++. Linking `libc++.a` directly
   would let `libc++abi`'s unnamespaced `__cxa_*` symbols capture the shim's exception handling.
   `scripts/link-extension.sh` therefore partially links the Lean side (bridge, Lean archives,
   `libc++.a`, `libc++abi.a`) with `ld -r`, then `objcopy --keep-global-symbols` localizes everything
   except `marien_bridge_*`. With that, the library depends only on `libstdc++`, `libm`,
   `libgcc_s`, `libc` and `ld-linux`, exports only `init` and `name`, and leaves only LadybugDB
   symbols undefined. 4.2 MB, 1.3 MB gzipped.
3. **Cause: local-exec TLS in the toolchain's `libleanrt.a`.** `LOAD` segfaults in `_dl_init` →
   `_mi_auto_process_init` → `mi_process_init_once` → `mi_thread_init` (mimalloc, inside
   `libleanrt.a`). Eight of the 35 objects in the toolchain's `libleanrt.a` (`alloc`, `interrupt`,
   `io`, `memory`, `mimalloc`, `object`, `stackinfo`, `thread`) carry local-exec TLS relocations
   (`TLSLE`/`TPREL`), which are valid only in the main executable. In a `dlopen`ed library their
   thread-pointer offsets are wrong. `libInit.a` (301 objects), `libStd.a` (270), `libLean.a` (848)
   and LeanElpi's objects have none.

4. **Fix: rebuild `libleanrt.a`.** `scripts/build-leanrt-pic.sh` checks out `src/runtime` at the
   toolchain's tag (v4.35.0) and the toolchain's mimalloc (v3.4.5, read from `lean/mimalloc.h`),
   and compiles the 35 runtime files plus mimalloc with the toolchain's Release flags, except
   `-fPIC -ftls-model=global-dynamic` and the system g++ with libstdc++ instead of the toolchain's
   libc++. It compiles against the toolchain's own `lean/config.h`, `lean.h` and `mimalloc.h`, and
   the system headers of the same GMP (6.3.0) and libuv (1.48.0) the toolchain ships, and takes
   the toolchain runtime's githash. `libLean.a`, `libInit.a` and `libStd.a` are plain C over
   `lean.h` (no `std::__1` symbol), so they link against it unchanged. The archive has 35
   objects, only TLSDESC relocations and no `TLSLE`/`TPREL`; the script refuses one that does.
   It takes about 9 s on 8 cores.
5. **Link with it.** `LEAN_RUNTIME_A=<archive> spike/build.sh` makes `scripts/link-extension.sh`
   use it instead of the toolchain's archive and drop the toolchain's `libc++.a`/`libc++abi.a`,
   so the whole library uses the host's libstdc++. Weak and unique symbols (libstdc++ template
   instantiations shared with the shim) stay global in the partial link so the final link can
   merge their COMDAT groups; the version script still keeps them out of the dynamic table.
   `spike/linux/run.sh` does all of this in a fresh container.

| Check (Linux aarch64, PIC runtime) | Result |
|---|---|
| Dependencies | `libstdc++.so.6`, `libm.so.6`, `libgcc_s.so.1`, `libc.so.6`, `ld-linux-aarch64.so.1` only |
| Exports | `init`, `name` only; undefined symbols are libc, libstdc++ and LadybugDB's only |
| Repeated loads (`stress load`) | runtime started once across two connections and a second database; first `LOAD` 8 ms |
| Failed init (`stress failinit`) | PASS |
| Stress | 16 × 1000: 0 failures, 0.52 s, RSS +8.4 MB; 16 × 4000: 0 failures, 2.06 s, RSS +8.3 MB |

| Release CLI | `CALL lean_ping()` answers 42 |

A second, clean-room run of `spike/linux/docker.sh` (fresh container) passed every check again, measuring a first `LOAD` of 41 ms and 2.2 s for 16 × 1000 calls; timings under Docker on macOS vary by a factor of four, so they are not a performance claim.

| Link (Linux aarch64) | Uncompressed | gzip -9 | xz -9 |
|---|---|---|---|
| `--gc-sections`, PIC runtime | 3.82 MB | 1.19 MB | 0.81 MB |
| no gc-sections, PIC runtime | 14.84 MB | 4.27 MB | not measured |

`libstdc++` symbols such as `__gxx_personality_v0` resolve to the release `liblbug.so`, which
exports its own copy; that is the host's choice and applies to every extension alike.

Shipping `libleanshared.so` next to the extension, as LeanElpi does on Linux, was rejected: it
is a second Lean shared library and its libc++abi would compete with libstdc++ for `__cxa_*` in
the global scope. Lean's own `leanrt_initial-exec` variant was not used: it is not shipped, and
initial-exec TLS in a `dlopen`ed library depends on glibc's static TLS surplus.
