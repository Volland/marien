Install

Download the zip for your platform from the download section, unzip it, and load the file by path. A build only loads into the LadybugDB release it was built for; any other release refuses it at LOAD.

LOAD EXTENSION '/path/to/libmarien.lbug_extension';
CALL elpi_init();

elpi_init creates Marien's system tables once per database: _elpi_module (one row per saved module), _elpi_accumulates (dependencies between modules) and _elpi_annotation. Calling it again changes nothing. Tables whose names start with _elpi_ are invisible to rules.

Your schema as types

Marien reads the catalog in your transaction and generates an ELPI signature from it. You never write it; rules are typechecked against it when you save them.

Modules

A module is ELPI source stored in _elpi_module, byte for byte. Saving it again creates a new version. A save typechecks the module against the signature, runs the analyses and stores their verdicts; anything that fails is refused and nothing is stored.

CALL elpi_save('org', 'pred manager_of i:person, o:person.
manager_of P M :- reports_to P _ M.');
CALL elpi_drop('org');                           // refused while another module accumulates it
CALL elpi_export() RETURN name, version, source;   // dependencies first
CALL elpi_import('[{"name": "org", "source": "…"}]');   // all or nothing
  • accumulate other. includes another saved module (or graph.std); cycles are refused, and a module cannot be dropped while others accumulate it.
  • Sources inside a Cypher string escape ' and \ with a backslash; the store keeps exactly the text Cypher reads.
  • MATCH (m:_elpi_module) RETURN m.name, m.version, m.status lists modules; status is ok, stale or broken (see schema changes).

Running rules

Typed entry points: elpi_run

A predicate declared with modes is an entry point. i: arguments come from a map of parameters named in1, in2, …; each o: argument becomes a column out1, out2, … whose type is fixed at bind time. A node comes back as its primary key, so it joins straight into a MATCH.

CALL elpi_run('kyc', 'ubo_of', {in1: 12})
WITH DISTINCT out2 MATCH (p:Person {id: out2}) RETURN p.name;

A missing, extra or ill-typed parameter fails the bind and names it. Every argument of a call must be a literal: LadybugDB does not pass query parameters to table functions.

Any goal: elpi_query

For writing and debugging rules: one row per solution and variable, with the binding as a JSON term, and exhausted telling whether the search finished.

CALL elpi_query('kyc', 'shareholder_of P _ (company 13), person.name P N')
RETURN sol, var, value, exhausted;

A call loads only the tables its entry point can reach, into a fresh store, inside your transaction: it sees your own uncommitted writes and nothing else. Calls are read-only.

Validation

A module takes part in validation when it declares exactly

pred violation o:severity, o:string, o:subject.            % severity: error, warning or info
pred violation_message i:string, i:subject, o:string.    % optional; the code is the message otherwise

elpi_validate runs every listed module (or all of them) and returns one row per solution: module, version, severity, code, message, subject_label (the subject's table) and subject_pk. A module that fails fails the call; a report is never partial.

CALL elpi_validate() RETURN *;                                     // every module
CALL elpi_validate(['kyc', 'hr']) RETURN *;                         // some modules
CALL elpi_validate(['kyc'], 'warning') RETURN *;                   // warning and error
CALL elpi_validate(['hr'], 'error', {Person: [1, 2]}) RETURN *;    // a narrowed scope, monotone modules only

Scopes and partitions

Narrowed scope

Pass a map from node tables to key lists to load only those nodes, their properties and the edges between listed endpoints; tables absent from the map load in full. Marien accepts a scope only for an entry point its analysis found monotone (no negation or cut over the database), because only then can a smaller graph give no wrong answer, only fewer. Narrowed rows carry narrowed = true.

CALL elpi_run('org', 'colleague', {in1: 7}, {Person: [7, 8, 9]}) RETURN *;

Anchor partitions

For rules that look a bounded distance from their subject. Declare the subject's kind and the radius; the save fails unless the locality check proves every atom a rule reads lies within that radius. Validation then runs batch by batch, each batch with its neighbourhood in a fresh store, and every subject lands in exactly one batch.

% @marien partition violation by person radius 1

Key partitions

For rules that compare rows sharing a value, such as uniqueness: rows are bucketed by a hash of the property, and each bucket is solved alone. Rows whose value is NULL form no bucket.

% @marien partition violation by person.email

CALL elpi_partition_batch=10000 sets the anchors per batch, and the rows per bucket.

graph.std

A library of combinators over relations, built into the extension: accumulate graph.std. A relation is a rel table's predicate (owns), or its projection without the edge term (edge_of owns).

CombinatorSucceeds
edge_of R X Ywhen R has an edge from X to Y
closure R X Yfor the transitive closure; terminates on cycles
symmetric_witness R X Yfor a pair related one way but not the other
functional_witness R X Y1 Y2for two distinct targets from one source
acyclic Rwhen R has no cycle
acyclic_witness R Xonce for each X on a cycle (searches; not local)
acyclic_witness_in C Xthe same, from the precomputed in_cycle.<rel>; local, so it partitions
card R X Min Maxwhen X has between Min and Max targets (-1: unbounded)
card_witness Nodes R Min Max X Nfor each node of Nodes (such as person) outside the bounds, with its count
violation error "no-manager" (subj_person X) :-
  card_witness person (edge_of has_manager) 1 1 X _.

Generated rules

Annotate tables with your own keys, then let meta-rules read the schema and the annotations to write clauses. An empty value removes an annotation.

CALL elpi_annotate('Owns', 'acyclic', 'true');

Meta-rules sit between % @marien meta and % @marien end and define pred generate o:string. Each solution is a piece of clause text. They see the schema as facts: schema.node T, schema.rel R From To, schema.prop T Column Type, schema.key T Column, schema.ident T Ident, schema.prop_ident T Column Ident and schema.annot T Key Value, and no data.

% @marien meta
pred generate o:string.
generate S :- schema.annot T "acyclic" "true", schema.ident T R,
  schema.rel T K _, schema.ident K N,
  S is "violation error \"cycle\" (subj_" ^ N ^ " X) :- acyclic_witness (edge_of " ^ R ^ ") X.".
% @marien end

Generation runs at save and whenever the schema or an annotation the module reaches changes. Its text is typechecked and analysed like source, stored in _elpi_module.generated, and bounded by fuel and elpi_max_generated_bytes, never by a clock, so the same schema always generates the same rules.

Schema changes

Each module stores a hash of the tables it reaches. LadybugDB has no hook for extensions to hear about DDL, so Marien checks lazily: a run whose hash differs recompiles the module first, and if it no longer typechecks the run fails with the error and its position. DDL on tables a module does not reach changes nothing for it.

CALL elpi_recheck();                    // every module: old_status, new_status, error
CALL elpi_recheck(['kyc']);             // some modules

elpi_recheck writes the result: ok again, or broken with the error, in one statement for all the modules it checks.

Statements

Each statement is syntax for one CALL, with the same columns, rows, errors and stored state. The rule source goes between dollar quotes and is stored byte for byte; use $tag$…$tag$ when it contains $$.

StatementSame as
CREATE [OR REPLACE] RULES org AS $$…$$elpi_save('org', '…')
DROP RULES orgelpi_drop('org')
CHECK RULESelpi_recheck()
VALIDATE [org, hr] [MIN SEVERITY warning]elpi_validate(['org', 'hr'], 'warning')
ANNOTATE Owns SET acyclic = 'true'elpi_annotate('Owns', 'acyclic', 'true')

For now, through elpi_statement. LadybugDB __LBUG__ passes only CREATE USER and CREATE ROLE to extension parsers, so write CALL elpi_statement('VALIDATE kyc MIN SEVERITY warning'). Marien registers its statement parser already; the plain syntax works once LadybugDB routes it (ladybug#1519). MIN SEVERITY needs module names.

Options and limits

Set with CALL <option>=<value> for the connection. A limit that is reached ends the call with an error naming it, never with a partial result; only elpi_max_solutions stops early, and says so.

elpi_timeout_ms0wall time per call; 0 is no deadline

Lean types offline

To prove things about your rules in Lean, generate Lean types from the same encoding. Dump the schema, then run the tool from a checkout of Marien:

CALL elpi_signature(format := 'json') RETURN text;   // save the text as schema.json

$ lake exe marien-codegen schema.json -o Schema.lean

The module has one inductive … deriving Elpi per kind and a program Schema.signature holding the runtime signature, so stored rules load against it unchanged. The tool elaborates the module and checks that the types deriving Elpi declares equal the ones the database uses; any difference fails it, naming the kind and constructor.
