Logic rules that live in your graph.

Marien is a LadybugDB extension that stores λProlog programs in the database, types them against the graph's schema, and runs them to query and validate the graph, all from Cypher.

Download v__VERSION__ Source on GitHub
Written in Lean 4 · runs LeanElpi · for LadybugDB __LBUG__

What it does

Your rules are saved as modules next to the data they reason about, and checked against the schema when you save them and again whenever the schema changes.

λTyped by the schema

Every node table, rel table and property becomes a λProlog type and predicate. A rule that misspells a property or mixes up types fails at save time, not at 3 a.m.

⊢Validation as a protocol

Declare violation in any module and elpi_validate runs all of them, returning one uniform report: severity, code, message and the offending node.

∂Analysed before it runs

Marien works out which tables a rule reaches, whether it is monotone, and how far from its subject it looks. It loads only what a rule needs and refuses scopes that would change the answer.

▦Partitioned for big graphs

Rules that stay near their subject run batch by batch, each in a fresh store with its own limits. Lean proves that every subject lands in exactly one batch, so no violation is reported twice.

From graph to verdict

A small org chart, one module of rules, then a typed query and a validation run.

1 · Load and set up
LOAD EXTENSION './libmarien.lbug_extension';
CALL elpi_init();    // creates Marien's module storage, once per database

CREATE NODE TABLE Person(id INT64 PRIMARY KEY, name STRING, title STRING);
CREATE REL TABLE ReportsTo(FROM Person TO Person);
2 · Save a module
CALL elpi_save('org', '
  pred manager_of i:person, o:person, o:string.
  manager_of P M T :- reports_to P _ M, person.title M T.

  pred violation o:severity, o:string, o:subject.
  violation error "no-manager" (subj_person P) :-
    person.name P _, not (reports_to P _ _).
  violation warning "no-title" (subj_person P) :-
    person P, not (person.title P _).
');
Types person, person.title and reports_to come from the schema; a typo here is a save error.
3 · Ask a typed question
CALL elpi_run('org', 'manager_of', {in1: 7})
WITH out2 MATCH (m:Person {id: out2})
RETURN m.name, out3;
→ ceo | CEO
4 · Validate the graph
CALL elpi_validate(['org']) WHERE severity = 'error'
RETURN code, subject_label, subject_pk;
→ no-manager | Person | 3
→ no-manager | Person | 9
