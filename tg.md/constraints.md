# Constraints

Facts nobody on this project chose: limits of LadybugDB, of LeanElpi and of the Lean runtime, plus the target scale. Each one forces one or more [[decisions]].

## Extensions are C++ shared libraries

LadybugDB loads extensions only as C++ shared libraries built against the exact database version that loads them; there is no stable extension ABI.

The loader `dlopen`s the file with `RTLD_NOW | RTLD_LOCAL` and looks up two C symbols: `name` (`const char*()`, used to skip an extension already loaded in that database) and `init` (`void(ClientContext*)`, which registers functions). On macOS official extensions link with `-undefined dynamic_lookup` and resolve LadybugDB symbols from the host, which both the release CLI and `liblbug` export. The generated header `common/system_config.h` comes from a CMake configure of the same tag and is part of the ABI. Release binaries use the OS C++ runtime (`/usr/lib/libc++.1.dylib` on macOS).

- source:: LadybugDB v0.22.1 `src/extension/extension.cpp`, `extension_manager.cpp` and `ladybugdb/extensions` CMakeLists; measured in `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Logic in Lean behind a thin C++ shim]]
- constrains:: [[decisions#Out-of-tree extension with its own repository]]

## Output columns are fixed at bind time

A LadybugDB table function declares its output columns and their types in its bind phase, before it executes.

- source:: `table_func_bind_t` in LadybugDB `src/include/function/table/table_function.h`
- constrains:: [[decisions#Typed entry points and an untyped debug query]]

## No DDL hooks for extensions

LadybugDB offers transformer, binder, planner, mapper and catalog extensions, but no event an extension can subscribe to when the schema changes.

- source:: LadybugDB `src/include/extension/`, checked 2026-10-31
- constrains:: [[decisions#Lazy recheck by schema hash]]

## Table functions can rewrite into Cypher

A standalone `CALL` may supply a `rewriteFunc` that turns its bind data into a Cypher statement, which is how an extension function can write without re-entering the database.

- source:: `table_func_rewrite_t` in LadybugDB `src/include/function/table/table_function.h:141`
- constrains:: [[decisions#CALL functions first]]
- constrains:: [[decisions#Rules stored in system tables]]

## Clause type variables are rigid

LeanElpi checks clauses against the declared type with its type variables rigid, so one polymorphic predicate cannot have clauses that each fix the variables differently.

- source:: lean-elpi `openspec/specs/elpi-typechecker/spec.md`, Requirement "Prenex polymorphism"
- constrains:: [[decisions#Staged rule generation over a reflected schema]]

## One Lean runtime per process

Each self-contained Lean shared library embeds `libleanrt`; loading two of them into one process gives two runtimes with separate global state.

The spike linked Marien's Lean code, LeanElpi, the Lean runtime, GMP and libuv statically into one extension and measured one runtime start across two connections and a second database in the same process.

- source:: lean-elpi `scripts/build-ffi.sh` and `openspec/changes/add-language-bindings/design.md`; `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Logic in Lean behind a thin C++ shim]]

## Out of fuel discards the search

In LeanElpi 0.3.3 `Step.outOfFuel` carries no machine, unlike `yield`, so a query that runs out of fuel cannot be resumed.

lean-elpi change `add-host-api` removes this limit with `Step.paused` and `Host.runSlice`; it holds until that change is released and Marien pins it.

- source:: lean-elpi `Elpi/Core/Machine.lean:94`, release 0.3.3
- constrains:: [[decisions#Fuel-sliced execution that fails loudly]]
- constrains:: [[decisions#Milestone order]]

## LeanElpi memory grows in long runs

LeanElpi uses 50 to 200 MB on ELPI's benchmarks, and nothing reclaims unification variables during a long run.

- source:: lean-elpi README, "Performance and compatibility", release 0.3.3
- constrains:: [[decisions#Partitioned validation]]
- constrains:: [[decisions#Materialize facts per call]]

## Target scale is 1M to 100M facts

Validation rules are expected to reach tables holding between one and one hundred million facts.

- source:: design interview, 2026-10-31
- constrains:: [[decisions#Partitioned validation]]

## Lean module initializers call lean_initialize

Code generated by Lean 4.35 calls `lean_initialize()` from every module initializer, and the toolchain's definition in `libleancpp` also initializes the whole Lean compiler package.

Linking that definition makes the extension about 25 times larger (68 MB instead of 2.7 MB, dead-stripped) although LeanElpi's core never uses the compiler.

- source:: generated `spike/.lake/build/ir/Spike.c` and `ld -why_live _initialize_Lean`, Lean 4.35.0; `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Runtime-only Lean initialization]]
- constrains:: [[components#Runtime bridge]]

## Official algo extension fails to load on macOS

The official `algo` extension package for LadybugDB 0.22 on macOS arm64 cannot be loaded: it needs `libnetworkit.dylib` through an rpath that points at the build machine.

- source:: `LOAD algo` with the v0.22.1 CLI, `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Scan tables in the calling transaction]] {note: "structural facts are computed by Marien's own shim, not by calling algo"}
- constrains:: [[components#Structural facts]]

## Linux Lean runtime archive is not dlopen-safe

The Lean 4.35 Linux toolchain's `libleanrt.a` uses local-exec thread-local storage in 8 of its 35 objects, which is valid only in the main executable; linked into an extension it crashes on load.

The same toolchain builds its runtime against its own static libc++, while LadybugDB on Linux uses libstdc++. `libInit.a`, `libStd.a`, `libLean.a`, GMP, libuv and LeanElpi have no local-exec TLS and no libc++ symbols.

Resolved in the build: `scripts/build-leanrt-pic.sh` recompiles the 35 runtime files and mimalloc at the toolchain's tag with `-fPIC`, global-dynamic TLS and the system libstdc++, against the toolchain's own `lean/config.h`, `lean.h` and `mimalloc.h`. `LEAN_RUNTIME_A` makes `scripts/link-extension.sh` use that archive and drop the toolchain's libc++. With it the spike passes every Linux check, at 3.8 MB (1.2 MB gzipped).

- source:: `readelf -rW` of the toolchain archives, a gdb backtrace into `mi_thread_init`, and the rebuilt archive's checks in Docker (Ubuntu 24.04, aarch64); `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Out-of-tree extension with its own repository]] {note: "Linux builds rebuild libleanrt with scripts/build-leanrt-pic.sh, once per Lean toolchain"}
- constrains:: [[components#Runtime bridge]] {note: "on Linux the Lean side is partially linked and localized; with the rebuilt runtime it shares the host's libstdc++"}
