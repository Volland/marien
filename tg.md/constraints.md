# Constraints

Facts nobody on this project chose: limits of LadybugDB, of LeanElpi and of the Lean runtime, plus the target scale. Each one forces one or more [[decisions]].

## Extensions are C++ shared libraries

LadybugDB loads extensions only as C++ shared libraries built against the exact database version that loads them; there is no stable extension ABI.

The loader `dlopen`s the file with `RTLD_NOW | RTLD_LOCAL` and looks up two C symbols: `name` (`const char*()`, used to skip an extension already loaded in that database) and `init` (`void(ClientContext*)`, which registers functions). On macOS official extensions link with `-undefined dynamic_lookup` and resolve LadybugDB symbols from the host, which both the release CLI and `liblbug` export. The generated header `common/system_config.h` comes from a CMake configure of the same tag and is part of the ABI. Release binaries use the OS C++ runtime (`/usr/lib/libc++.1.dylib` on macOS).

- source:: LadybugDB v0.22.1 `src/extension/extension.cpp`, `extension_manager.cpp` and `ladybugdb/extensions` CMakeLists; measured in `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Logic in Lean behind a thin C++ shim]]
- constrains:: [[decisions#Out-of-tree extension with its own repository]]

## Output columns are fixed at bind time

A LadybugDB table function declares its output columns and their types in its bind phase, before it executes.

- source:: `table_func_bind_t` in LadybugDB `src/include/function/table/table_function.h`
- constrains:: [[decisions#Typed entry points and an untyped debug query]]

## No DDL hooks for extensions

LadybugDB offers transformer, binder, planner, mapper and catalog extensions, but no event an extension can subscribe to when the schema changes.

- source:: LadybugDB `src/include/extension/`, checked 2026-10-31
- constrains:: [[decisions#Lazy recheck by schema hash]]

Proposed upstream as a listener called in the DDL's transaction: LadybugDB/ladybug#1518 (`docs/upstream/catalog-change-hook.md`, 2026-11-06).

## Table functions can rewrite into Cypher

A standalone `CALL` may supply a `rewriteFunc` that turns its bind data into a Cypher statement, which is how an extension function can write without re-entering the database.

- source:: `table_func_rewrite_t` in LadybugDB `src/include/function/table/table_function.h:141`
- constrains:: [[decisions#CALL functions first]]
- constrains:: [[decisions#Rules stored in system tables]]

## Clause type variables are rigid

LeanElpi checks clauses against the declared type with its type variables rigid, so one polymorphic predicate cannot have clauses that each fix the variables differently.

- source:: lean-elpi `openspec/specs/elpi-typechecker/spec.md`, Requirement "Prenex polymorphism"
- constrains:: [[decisions#Staged rule generation over a reflected schema]]
- constrains:: [[components#Rule generator]] {strength: must, note: "rule-generation, Stage one meta-rules: the description is plain data"}
- constrains:: [[decisions#Combinators take the node predicate where they enumerate nodes]] {strength: must}

## One Lean runtime per process

Each self-contained Lean shared library embeds `libleanrt`; loading two of them into one process gives two runtimes with separate global state.

The spike linked Marien's Lean code, LeanElpi, the Lean runtime, GMP and libuv statically into one extension and measured one runtime start across two connections and a second database in the same process.

- source:: lean-elpi `scripts/build-ffi.sh` and `openspec/changes/add-language-bindings/design.md`; `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Logic in Lean behind a thin C++ shim]]

## Out of fuel discards the search

In LeanElpi 0.3.3 `Step.outOfFuel` carries no machine, unlike `yield`, so a query that runs out of fuel cannot be resumed.

lean-elpi change `add-host-api` removes this limit with `Step.paused` and `Host.runSlice`; it holds until that change is released and Marien pins it.

- source:: lean-elpi `Elpi/Core/Machine.lean:94`, release 0.3.3
- constrains:: [[decisions#Fuel-sliced execution that fails loudly]]
- constrains:: [[decisions#Milestone order]]

## LeanElpi memory grows in long runs

LeanElpi uses 50 to 200 MB on ELPI's benchmarks, and nothing reclaims unification variables during a long run.

- source:: lean-elpi README, "Performance and compatibility", release 0.3.3
- constrains:: [[decisions#Partitioned validation]]
- constrains:: [[decisions#Materialize facts per call]]

## Target scale is 1M to 100M facts

Validation rules are expected to reach tables holding between one and one hundred million facts.

- source:: design interview, 2026-10-31
- constrains:: [[decisions#Partitioned validation]]
- constrains:: [[decisions#Milestone order]]

## Lean module initializers call lean_initialize

Code generated by Lean 4.35 calls `lean_initialize()` from every module initializer, and the toolchain's definition in `libleancpp` also initializes the whole Lean compiler package.

Linking that definition makes the extension about 25 times larger (68 MB instead of 2.7 MB, dead-stripped) although LeanElpi's core never uses the compiler.

- source:: generated `spike/.lake/build/ir/Spike.c` and `ld -why_live _initialize_Lean`, Lean 4.35.0; `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Runtime-only Lean initialization]]
- constrains:: [[components#Runtime bridge]]

## Official algo extension fails to load on macOS

The official `algo` extension package for LadybugDB 0.22 on macOS arm64 cannot be loaded: it needs `libnetworkit.dylib` through an rpath that points at the build machine.

- source:: `LOAD algo` with the v0.22.1 CLI, `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Scan tables in the calling transaction]] {note: "structural facts are computed by Marien's own shim, not by calling algo"}
- constrains:: [[components#Structural facts]]

## Linux Lean runtime archive is not dlopen-safe

The Lean 4.35 Linux toolchain's `libleanrt.a` uses local-exec thread-local storage in 8 of its 35 objects, which is valid only in the main executable; linked into an extension it crashes on load.

The same toolchain builds its runtime against its own static libc++, while LadybugDB on Linux uses libstdc++. `libInit.a`, `libStd.a`, `libLean.a`, GMP, libuv and LeanElpi have no local-exec TLS and no libc++ symbols.

Resolved in the build: `scripts/build-leanrt-pic.sh` recompiles the 35 runtime files and mimalloc at the toolchain's tag with `-fPIC`, global-dynamic TLS and the system libstdc++, against the toolchain's own `lean/config.h`, `lean.h` and `mimalloc.h`. `LEAN_RUNTIME_A` makes `scripts/link-extension.sh` use that archive and drop the toolchain's libc++. With it the spike passes every Linux check, at 3.8 MB (1.2 MB gzipped), and so does the tracer bullet's extension (4.5 MB, 1.46 MB gzipped; `tests/linux/run.sh`, all 33 integration tests).

- source:: `readelf -rW` of the toolchain archives, a gdb backtrace into `mi_thread_init`, and the rebuilt archive's checks in Docker (Ubuntu 24.04, aarch64); `spike/RESULT.md`, 2026-10-31
- constrains:: [[decisions#Out-of-tree extension with its own repository]] {note: "Linux builds rebuild libleanrt with scripts/build-leanrt-pic.sh, once per Lean toolchain"}
- constrains:: [[components#Runtime bridge]] {note: "on Linux the Lean side is partially linked and localized; with the rebuilt runtime it shares the host's libstdc++"}


## Rewrite functions take literals only

LadybugDB runs a table function's bind and `rewriteFunc` while parsing, before parameter values are bound, so a rewriting function sees literal arguments only; a `$param` binds as an untyped null.

Only a bare `CALL f(...)` is rewritten; `CALL f(...) RETURN *` runs the function's `tableFunc` instead. In autocommit mode bind and rewrite run in their own read-only transaction, which commits before the rewritten statements run.

- source:: LadybugDB v0.22.1 `src/parser/visitor/standalone_call_rewriter.cpp:25-51`, `src/binder/expression_binder.cpp:139-156`, `src/function/table/bind_input.cpp:14-17`
- constrains:: [[components#Extension shim]] {strength: must, note: "elpi_save(name, source) takes string literals (rule-storage, Save checks before storing)"}
- constrains:: [[decisions#One rewritten statement per write]]

## A rewrite is a batch of statements

The text `rewriteFunc` returns is parsed as a new batch: several `;`-separated statements may follow each other, each in its own auto transaction, so a batch is atomic only inside an explicit transaction.

A single statement may chain `MERGE`, `SET`, `OPTIONAL MATCH ... DELETE`, `UNWIND`, `MATCH` and `CREATE` with `WITH`, and is atomic on its own (checked against the 0.22.1 CLI on 2026-10-31).

- source:: LadybugDB v0.22.1 `src/main/client_context.cpp:467-547`; `Cypher.g4:337-351`
- constrains:: [[decisions#One rewritten statement per write]] {strength: must}
- constrains:: [[components#Module store]] {strength: must, note: "elpi_import and elpi_init return several statements (rule-storage, Export and import)"}

## A pred declaration replaces a constant of the same name

In LeanElpi a `type` declaration of a name already declared adds an overload, but a later `pred` declaration replaces the constant; overloading a constructor and a predicate works only with the `pred` first.

- source:: lean-elpi `Elpi/Core/Typecheck.lean:150-170` (`overloads`); probed with `Marien.Engine.compile`, 2026-10-31
- constrains:: [[components#Signature generator]] {strength: must, note: "emit pred t before type t"}
- constrains:: [[components#Offline codegen]] {strength: must, note: "derived type declarations come first, so the emitted program re-accumulates the runtime signature"}

## Derived declarations come before accumulated units

LeanElpi assembles a program from the `kind`/`type` declarations every `deriving Elpi` registered, then the units accumulated into it; a program cannot place its own declarations ahead of the derived ones.

With a derived `type person int -> person`, an accumulated `pred person o:person.` replaces the constructor (see [[constraints#A pred declaration replaces a constant of the same name]]), so rules using `person 7` fail to typecheck.

- source:: lean-elpi `Elpi/Lean/Commands.lean` (`assemble`) and `Elpi/Runtime/Dsl.lean` at the pinned commit; probed with a generated module, 2026-11-06
- constrains:: [[components#Offline codegen]] {strength: must, note: "the emitted program accumulates the whole runtime signature, whose type declarations restore each overload"}
- constrains:: [[decisions#The generated module accumulates the runtime signature]] {strength: must}

## Importing resets initializer execution

In Lean 4.35, `importModules` (and `processHeader`) clears the flag that `enableInitializersExecution` sets, so a second import in the same process fails with "`enableInitializersExecution` must be run before calling `importModules`".

- source:: Lean 4.35 `Lean/ImportingFlag.lean` (`withImporting`) and `Lean/Compiler/InitAttr.lean`, 2026-11-06
- constrains:: [[components#Offline codegen]] {strength: must, note: "the imported header environment is cached and reused for every module elaborated in one process"}

## Names starting with an underscore are variables

ELPI reads every identifier that starts with `_` or an upper-case letter as a variable, so the name of a system table such as `_elpi_module.source` can never be written as a constant in a module.

- source:: ELPI lexical conventions; lean-elpi `Elpi/Core/Lexer.lean`
- constrains:: [[components#Signature generator]] {strength: must, note: "system tables cannot be named in rules; every part of a generated name must start with a lower-case letter (schema-encoding, Injective naming)"}

## LeanElpi integers are unbounded

LeanElpi represents ELPI `int` values as Lean `Int`, so every LadybugDB integer, UINT64 and INT128 included, maps to an `int` without loss or range check.

- source:: lean-elpi `Elpi/Core/Term.lean:30` (`int (i : Int)`)
- constrains:: [[components#Value codec]] {strength: must, note: "no range check (schema-encoding, Property type mapping)"}

## INSTALL accepts only official extensions

LadybugDB 0.22.1 binds `INSTALL <name>` and `LOAD <name>` only for names on its built-in list of official extensions; any other name is refused before anything is downloaded.

Other extensions load by path with `LOAD EXTENSION '<path>'`. The installer's download layout is `<repo>v<extension version>/<os>_<arch>/<name>/lib<name>.lbug_extension`, with extension version 0.22.0 for release 0.22.1.

- source:: `src/binder/bind/bind_extension.cpp` and `src/extension/extension.cpp` of LadybugDB v0.22.1; `scripts/test-install.sh`, 2026-11-01
- constrains:: [[decisions#Out-of-tree extension with its own repository]] {strength: must, note: "INSTALL marien FROM <url> needs LadybugDB to accept third-party names; until then users download from the server layout and LOAD EXTENSION by path"}
- constrains:: [[components#Extension shim]] {note: "published in the installer's layout so it works once INSTALL accepts it"}

## The CLI does not export the release version

LadybugDB's CLI binary does not export `lbug::main::Version::getVersion`; liblbug does. Both export `StorageVersionInfo::getStorageVersion`, and storage version 49 covers both 0.22.0 and 0.22.1.

An extension that calls `getVersion` directly fails to load into the CLI with an unresolved symbol.

- source:: `nm -gU` of the v0.22.1 CLI and liblbug (macOS arm64), and a failed `LOAD EXTENSION` in the CLI, 2026-11-01
- constrains:: [[components#Extension shim]] {strength: must, note: "version symbols are looked up with dlsym at load time"}

## Deep indexing scans the first-argument bucket

LeanElpi's first-argument index keys a fact by the outer constructor of its first argument; a deeper `:index` only filters that bucket by hash. A lookup among loaded facts stays linear in their number.

Every node term is `person <key>`, so all facts of a table share one bucket: a join at full scope is quadratic (one rule at 5000, 10000 and 20000 persons: 0.5, 2 and 8 seconds).

- source:: `Elpi/Core/Index.lean` (`PredDB.select`) of the pinned lean-elpi, and timings with the CLI, 2026-11-01
- constrains:: [[components#Executor]] {strength: must, note: "full-scope joins are quadratic"}
- constrains:: [[components#Partition planner]] {strength: should, note: "small batches keep each store small"}
- constrains:: [[decisions#Generated predicates are indexed to depth 2]]

## Table function arguments are literals

Every argument of a table function call must be a literal: `CALL elpi_run('c', 'q', NULL, $scope) RETURN *` fails to prepare with "has type PARAMETER but LITERAL was expected", even for a function that does not rewrite.

A narrowed scope therefore cannot be a query parameter, as the rule-execution spec expects; a caller writes the key list into the statement.

- source:: a prepared statement with a bound STRUCT parameter against LadybugDB v0.22.1 liblbug (macOS arm64), 2026-11-01
- constrains:: [[components#Extension shim]] {strength: must, note: "the scope of elpi_run and elpi_validate is a literal"}

## Table is a reserved word

LadybugDB's parser refuses `table` as a property name (`CREATE NODE TABLE … (table STRING)` is a parse error), so a system table cannot have a column called `table`.

- source:: LadybugDB 0.22.1 parser, checked in the CLI
- constrains:: [[components#Module store]] {strength: must, note: "schema-reflection, Schema annotations: the column is table_name"}

## Only CREATE USER and CREATE ROLE reach extension parsers

LadybugDB parses every statement with its own ANTLR grammar first; its Transformer hands a parse tree to extension transformers only for `CREATE USER` and `CREATE ROLE`, and nothing rewrites query text before parsing.

New statement syntax such as `CREATE RULES org AS $$…$$` is therefore a syntax error before any extension sees it; the Binder, Planner and Mapper hooks only receive statements that a transformer produced.

- source:: LadybugDB v0.22.1 and `main` (2026-11-06): `src/parser/transformer.cpp` (`transformExtensionStatement`, called for `iC_CreateUser` and `iC_CreateRole` only), `src/antlr4/Cypher.g4` (`oC_Statement`), `src/main/client_context.cpp` (`parseQuery`)
- constrains:: [[components#Statement extension]] {strength: must, note: "no route from new syntax to the extension hooks without a grammar change upstream (custom-statements, Rule statements)"}

Proposed upstream as a text-level fallback for extension transformers, with the parse node classes exported: LadybugDB/ladybug#1519 (`docs/upstream/extension-statements.md`).

## ld64 drops dead stripping when one object lacks subsections

Apple's linker keeps `MH_SUBSECTIONS_VIA_SYMBOLS` in a partial link (`ld -r`) only when every input has it; GMP's assembly objects do not, and without the flag the final link cannot dead-strip.

A private extern definition is also left out of an archive's table of contents, so an archive member whose symbols are all private extern is never pulled. Merging Marien's Lean side with GMP in one object made the extension 13.8 MB instead of 4 MB.

- source:: `otool -hv` of partial links of the Lean archives with and without `libgmp.a`, Xcode ld64 on macOS 15, arm64, 2026-11-06
- constrains:: [[components#Runtime bridge]] {strength: must, note: "the prebuilt archive is two objects on macOS: the Lean side with only marien_bridge_* global, and GMP/libuv with the functions it calls global"}
